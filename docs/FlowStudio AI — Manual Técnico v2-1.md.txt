## 1. VISÃO GERAL E MODELO DE NEGÓCIO

O FlowStudio AI é uma plataforma white-label de alto desempenho, projetada especificamente para atender às necessidades de studios de beleza, barbearias e centros de estética. O sistema opera sob um modelo de **ISOLAMENTO TOTAL POR CLIENTE**, garantindo máxima segurança, performance e personalização para cada studio.

Cada studio cliente do FlowStudio AI possui uma instância completamente dedicada e isolada, composta por:

- **Deploy Independente:** Cada studio tem seu próprio deploy no Netlify, assegurando autonomia e performance otimizada.
- **Banco de Dados Dedicado:** Um projeto isolado no Supabase, incluindo PostgreSQL, autenticação (Auth) e Row Level Security (RLS).
- **Identidade Visual Personalizada:** Configurações de branding e landing pages exclusivas em `src/sites/<slug>/`, permitindo identidade própria.

### 1.1 Estrutura de Módulos

O sistema é arquitetado em dois núcleos fundamentais:

1. **Sistema (Core):** Localizado em `src/lib/` e `src/features/`, contém a lógica de negócio compartilhada, componentes de interface administrativa e integrações de infraestrutura. Representa o núcleo comum.
2. **Site (Studio):** Localizado em `src/sites/<slug>/`, gerencia a presença digital pública de cada studio e consome o core através de fachadas.

**REGRA DE OURO DA MODULARIDADE:**
É estritamente proibido que `src/lib/` importe diretamente de `src/sites/`. Em vez disso, `src/sites/` DEVE consumir funcionalidades de `src/lib/core/` exclusivamente via fachadas como `buildBrandingCss.ts` e `buildSeo.ts`.

## 2. ARQUITETURA GERAL

**Fluxo de dados:** Internet → Netlify SSR → TanStack Start + Router → React Query + Server Functions → Supabase (PostgreSQL, Auth, Storage, RLS)

**Componentes:**
- **Netlify SSR:** Hospedagem com suporte a Server-Side Rendering para SEO e performance. Cada studio tem deploy independente.
- **TanStack Start + Router:** Roteamento tipado e gerenciamento de estado.
- **React Query + Server Functions:** Camada de abstração para API e mutações.
- **Supabase:** Backend-as-a-Service (PostgreSQL, Auth, Storage, RLS).

### 2.1 ATUALIZAÇÃO v2.1 — Marco Desvinculo Site x Sistema

- `__root.tsx`: Tornou-se shell neutro absoluto. Removidos tema, SEO, fonts, JSON-LD e styleHrefs específicos do site.
- `_auth.tsx`: Zona de sistema para telas de autenticação (sem guard).
- `_authed.tsx`: Aplica systemThemeClass + guard de sessão/role. Sem sessão ativa → redireciona para `/login`. Role negada → `/login`.
- `index.tsx`: Rota raiz `/` absorve identidade do studio (tema, SEO, OpenGraph, JSON-LD).
- Auth funcional e testada.
- Zonas congeladas: `src/sites/ruah/` não recebe alterações de feature (somente landing page).

### 2.2 ATUALIZAÇÃO v2.2 — Multi-Serviço no Agendamento

- **Nova tabela `appointment_services`**: armazena N serviços por agendamento (snapshot nome/duração/preço + quantidade).
- **`appointments.service_id` tornou-se NULLABLE**: em agendamentos multi-serviço, `service_id` fica `NULL` e a fonte da verdade passa a ser `appointment_services`. Agendamentos legados de 1 serviço mantêm `service_id` preenchido (backfill).
- **Novas RPCs SQL**: `create_appointment_multi_service` e `update_appointment_multi_service` (transacional, calculam `ends_at` e `price` somando duração/preço × quantidade).
- **Novo componente `ServicePicker`**: grid de cards de serviços no molde do PDV (busca + badge de quantidade + listinha de selecionados com total).
- **Server functions**: `createAppointmentMulti` / `updateAppointmentMulti` (wrappers Zod → RPC).
- **Relatório de receita por serviço** (`get_revenue_by_service_report`) passou a ler de `appointment_services`.

## 3. STACK TECNOLÓGICA

### 3.1 Tecnologias Core
- **Framework:** TanStack Start (SSR) + TanStack Router + TanStack React Query
- **Backend:** Supabase (PostgreSQL, Auth, Storage, Row Level Security)
- **Linguagem:** TypeScript com `noUncheckedIndexedAccess: true`
- **Estilização:** Tailwind CSS + Framer Motion + Radix UI
- **Build/Ferramentas:** Vite + PostCSS
- **Infraestrutura:** Netlify (SSR Functions + deploy automatizado)
- **Utilitários:** lucide-react (ícones), sonner (toasts), zod (validação)

### 3.2 Adições v2.0, v2.1 e v2.2 (mantidas)
- **Zustand:** Gerenciamento de estado global leve para UI
- **Date-fns:** Manipulação e formatação de datas
- **Recharts:** Visualização de dados e gráficos
- **IDB (IndexedDB):** Cache local para persistência offline

### 3.3 Tecnologias Proibidas
- Redux (substituído por React Query/Zustand)
- Axios (substituído por fetch nativo em Server Functions)
- Bibliotecas de UI pesadas sem suporte a Tailwind
- Microsserviços, multi-tenant de banco único, Kubernetes, filas de mensagens complexas, CQRS, Event Sourcing

### 7.4 Funções SQL

**Multi-serviço (NOVO v2.2):**

- `create_appointment_multi_service(p_client_id uuid, p_staff_id uuid, p_starts_at timestamptz, p_services jsonb, p_notes text DEFAULT NULL, p_status appointment_status DEFAULT 'pending', p_payment_method_id uuid DEFAULT NULL) RETURNS uuid`
  - Valida ao menos 1 serviço; itera `p_services` (array jsonb `[{serviceId, quantity}]`) somando `duration_minutes × quantity` e `price × quantity`.
  - Insere em `appointments` com `service_id = NULL`, `ends_at = starts_at + duração total`, `price = preço total`.
  - Insere um registro em `appointment_services` por serviço (snapshot nome/duração/preço + quantidade).
  - `SECURITY DEFINER`, `search_path = 'public'`. Retorna o `id` do agendamento.

- `update_appointment_multi_service(p_appointment_id uuid, p_client_id uuid, p_staff_id uuid, p_starts_at timestamptz, p_services jsonb, p_notes text DEFAULT NULL, p_status appointment_status DEFAULT NULL) RETURNS void`
  - Recalcula `ends_at` e `price` a partir dos serviços.
  - Atualiza `appointments` (status via `COALESCE(p_status, status)`).
  - **DELETE + reinsert** dos itens em `appointment_services` (estratégia de substituição total).
  - `SECURITY DEFINER`, `search_path = 'public'`.

**Relatório (v2.2):**

- `get_revenue_by_service_report(p_start_date date, p_end_date date) RETURNS TABLE(service_id, service_name, service_category, quantity, revenue, percentage)`
  - **Lê de `appointment_services`** (join com `appointments` filtrando status `completed`/`confirmed`), agregando `SUM(quantity)` e `SUM(price × quantity)` por serviço. Percentual sobre o total.

**Demais functions (mantidas):**

- `current_user_role()`: Retorna a role do usuário logado (usada em RLS).
- `handle_appointment_lifecycle()`: Trigger que valida `payment_method_id` ao concluir e recalcula agregados do cliente. **Não insere mais finance_transactions** (agora via `finalize_sale`).
- `check_appointment_conflict()`: Trigger que bloqueia conflito com folga e com outro agendamento ativo do mesmo profissional.
- `maintain_client_metrics()`: Recalcula `first_visit`, `last_visit`, `total_visits`, `total_spent`, `frequency_days`.
- `recalc_client_aggregates(p_client_id)`: Recalcula `total_appointments`, `total_spent`, `last_visit_at`.
- `finalize_sale` / `finalize_sale_v2`: Finalizam venda, geram financeiro e atualizam appointment para `completed`.
- `normalize_phone_br` / `normalize_phone_before_write`: Normalização de telefone.
- `handle_new_user`: Cria profile + vincula/associa client no cadastro.
- `get_appointments_count`, `get_cash_flow_report`, `get_cash_flow_report_daily`, `get_expenses_by_category_report`, `get_new_vs_returning_report`, `get_occupancy_rate_report`, `get_operational_overview`, `get_staff_performance_report`, `get_top_products_report`, `get_clients_by_birth_month`: Relatórios gerenciais.
- `settle_commissions(p_transaction_ids uuid[])`: Acerto de comissões.
- `set_updated_at`: Trigger genérico de timestamp.
- `rls_auto_enable`: Event trigger que habilita RLS em tabelas novas.

**Detalhe `createAppointmentMulti` (v2.2):**
- Valida com Zod: `clientId`, `staffId`, `startsAt`, `services[]` (mín. 1, cada item `{serviceId, quantity}`), `notes?`, `status?`, `paymentMethodId?`.
- Verifica sessão (`supabase.auth.getUser()`).
- Chama `supabase.rpc('create_appointment_multi_service', {...})`.
- Erros normalizados e logados.

**Detalhe `getDayAppointments` (v2.2):**
- `select` com join em `clients`, `services`, `appointment_services` e `staff(profiles)`.
- `mapRow`: monta `services: AppointmentServiceItem[]` a partir de `appointment_services`; `serviceId` = `NULL` quando há itens (multi), senão fallback `service_id`; `serviceName` = "Múltiplos serviços" quando 2+, senão snapshot/legado.

### 8.2 dashboard/ (2 funções)

## 12. CONVENÇÕES E PADRÕES

### 12.1 Arquitetura Baseada em Features
Cada feature em `src/features/<nome>/` segue: `components/`, `hooks.ts`, `server/`, `types.ts`, `utils/`, `index.ts`.

### 12.2 Regras de Engenharia
- Sem acesso direto ao Supabase via React (sempre `createServerFn`)
- SQL inline proibido (toda query via Server Functions)
- Features autocontidas
- Invalidar Query Keys após mutations
- Mobile First
- SSR Safe
- Tipagem 100% (TypeScript strict, sem any)
- Zod para validação de schemas em Server Functions

### 12.3 Convenção de Query Keys

```
['sales', 'draft', { appointmentId }]
['services', 'list']
['dashboard', 'data', { period }]
['dayTimeOff']
```

### 12.4 Regras de UI
- Mobile-first: toda interface responsiva

- framer-motion: animações suaves
- active:scale-95: feedback tátil em botões

## 13. FLUXOS DE TRABALHO

### 13.1 Fluxo de Agendamento (v2.2 — multi-serviço)

1. Cliente acessa BookingWizard (ou admin agenda manualmente)
2. Passo 1: Seleciona serviço (`listActiveServices`)
3. Passo 2: Seleciona profissional (`listBookableStaff`)
4. Passo 3: Escolhe data/horário (`getAvailableSlots`)
5. Passo 4: Confirma dados (`createAppointment`)
6. **Admin (novo agendamento):** `AppointmentFormModal` → `ServicePicker` seleciona 1+ serviços com quantidade; `endTime` auto-derivado da soma das durações
7. **Criação:** `useCreateAppointmentMulti` → `createAppointmentMulti` → RPC `create_appointment_multi_service` (calcula `ends_at` + `price`, grava itens em `appointment_services`)
8. Agendamento aparece na Agenda do admin (`getDayAppointments` — lê `appointment_services`)
9. Profissional realiza atendimento
10. Admin conclui agendamento e abre PDV (`getAppointmentSaleData` — lê multi-serviço)
11. PDV: adiciona produtos, aplica split de pagamento
12. `createSale`/`finalize_sale` finaliza venda → gera `finance_transactions`
13. Appointment status alterado para `completed`
14. Trigger `handle_appointment_lifecycle` dispara eventos CRM

### 13.2 Fluxo do PDV
1. Agendamento concluído ou venda avulsa
2. Carrinho: adicionar produtos/serviços
3. Aplicar descontos se necessário
4. SplitPayment: dividir valor entre formas de pagamento
5. Confirmar venda (`createSale`)
6. `createSaleDraft` para rascunhos
7. Transação financeira registrada em `finance_transactions`
8. Estoque de produtos atualizado
9. Status do appointment atualizado para `completed`
10. CRM Log gerado para registro

### 13.3 Fluxo do CRM
1. Evento detectado (appointment no_show, aniversário, cliente sem retorno há 45+ dias)
2. Evento registrado em `client_events`
3. Motor de tarefas do CRM avalia o evento
4. Tarefa gerada e registrada em `crm_logs`
5. Notificação enviada ao admin
6. Admin executa ação (contato, oferta, etc.)
7. Tarefa marcada como resolvida
8. Dashboard atualizado com métricas de CRM
